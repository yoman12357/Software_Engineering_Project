# ADR-0003: Structured JSON Before Document Rendering

**Status:** Accepted
**Date:** 2026-08-07
**Deciders:** Project Architect

---

## Context

CyberSRS uses an LLM to generate SRS content (requirements, threat models, architecture descriptions, acceptance criteria). This generated content must ultimately be:

1. Displayed in a structured, navigable UI for review and editing.
2. Validated for completeness, testability, and consistency.
3. Rendered into a professional PDF document.
4. Stored for version history and comparison.

A fundamental design question is: **what is the canonical representation of the generated SRS?**

- Option A: Free-form text (Markdown or plain text) generated by the LLM, later parsed for display and PDF.
- Option B: Structured JSON generated by the LLM, validated against a schema, then rendered into UI and PDF.

## Decision

**Structured JSON is the canonical representation of all LLM-generated SRS content.**

Every LLM call that produces SRS content must return its output as JSON conforming to a predefined Pydantic model. The JSON is validated immediately. Only valid JSON is stored, displayed, or rendered.

The flow is:

```
LLM generates JSON → Pydantic validation → Store in SQLite → Render to UI → Render to PDF
```

Never:

```
LLM generates text → Display raw text → Try to parse for PDF
```

## Alternatives Considered

| Alternative | Reason for Rejection |
|---|---|
| **Free-form Markdown output** | Parsing Markdown into structured data for editing, validation, and PDF is fragile and error-prone. Loses traceability. |
| **Free-form text + post-processing parser** | The parser becomes a complex, brittle component. Errors in parsing corrupt the data. |
| **HTML output from LLM** | Security risk (XSS); parsing HTML is harder than validating JSON; not suitable for structured editing. |
| **XML output** | More verbose than JSON; less natural for LLMs; less ecosystem support in Python. |

## Consequences

### Positive

- **Reliable validation.** JSON schemas (Pydantic models) catch structural errors immediately. Invalid output triggers a retry with a corrective prompt rather than silently corrupting downstream data.
- **Clean editing.** Individual fields (requirement statement, priority, rationale) can be edited independently in the UI because they are discrete JSON fields, not substrings of a text blob.
- **Deterministic PDF rendering.** The PDF template reads structured fields. No fragile text parsing needed. Layout is consistent and professional.
- **Version comparison.** JSON diffs are precise — you can see exactly which requirement changed, not just which paragraph changed.
- **Traceability.** Each requirement has a stable ID in the JSON. Sources, threats, and acceptance criteria link to requirements by ID.
- **Testability.** Schema validation tests can verify all LLM outputs automatically.

### Negative

- **Harder for the LLM.** Generating valid JSON is more challenging for LLMs than generating free-form text, especially for smaller models. Mitigated by:
  - Detailed prompt templates with JSON examples.
  - Schema included in the prompt.
  - Corrective-prompt retry logic (up to configurable max retries).
  - QLoRA fine-tuning specifically targets JSON-structured output.
- **More complex prompts.** Prompts must specify the exact JSON structure. Increases prompt length and token usage.
- **Risk of JSON truncation.** If the LLM's context window is too small for the full SRS JSON, output may be truncated. Mitigated by generating sections independently rather than the entire SRS in one call.

### Neutral

- This decision does not prevent displaying a rendered (Markdown or HTML) view of the SRS in the UI. The UI renders the JSON into a human-readable format. The JSON remains the source of truth.
