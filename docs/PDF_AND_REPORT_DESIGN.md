# PDF and Report Design — CyberSRS

**Version:** 0.1.0-draft
**Date:** 2026-08-07
**Status:** Phase 0 — Planning

> The PDF generator consumes **validated SRS JSON only** (ADR-0003). It never renders raw LLM output.

---

## 1. Source JSON

The PDF is generated exclusively from the `srs_json` field of a validated `SRSVersion` record.

**Input contract:**
- The `SRSVersion.status` must be `validated` or `approved` before export (SEC-044).
- The JSON must have passed Pydantic validation against the SRS schema (DATA_MODEL.md §3).
- The PDF renderer receives a Python `SRSVersion` Pydantic model, not a raw JSON string.

---

## 2. Template Layers

The PDF uses a layered template approach:

| Layer | Responsibility |
|---|---|
| **Document template** | Page size, margins, fonts, headers, footers, page numbers. |
| **Section templates** | Layout for each SRS section (requirements table, threat table, architecture description). |
| **Component templates** | Reusable elements: requirement row, threat card, citation reference, traceability cell. |

**Technology decision:** PDF library is unresolved (UDEC-002). Candidates: WeasyPrint, ReportLab, FPDF2. The design is library-agnostic at this stage.

| 4 | **Project Summary** | `project_summary` | Yes |
| 5 | **Functional Requirements** | `functional_requirements` | Yes |
| 6 | **Non-Functional Requirements** | `non_functional_requirements` | Yes |
| 7 | **Security Requirements** | `security_requirements` | Yes |
| 8 | **System Architecture** | `system_architecture` | Yes |
| 9 | **Threat Model** | `threat_model` | Yes |
| 10 | **Acceptance Criteria** | `acceptance_criteria` | Yes |
| 11 | **Testing Recommendations** | `testing_recommendations` | Yes |
| 12 | **Validation Report** | `validation_report` | Yes |

## 4. Table of Contents

- Auto-generated from section headings.
- Includes page numbers.
- Links to section starts (if the PDF library supports internal links).
- Two levels of depth: section titles and subsections (e.g., "5. Functional Requirements" → "5.1 Project Management").

## 5. Requirement Tables

Each requirement category (FR, NFR, SEC) is rendered as a table:

| Column | Source field | Width (approx.) |
|---|---|---|
| ID | `requirement_id` | 10% |
| Title | `title` | 15% |
| Statement | `statement` | 30% |
| Priority | `priority` | 8% |
| Acceptance Criteria | `acceptance_criteria` | 25% |
| Sources | `source_references` (abbreviated) | 12% |

**Source abbreviation:** Instead of full source details, show `[1]`, `[2]`, etc., with a legend at the bottom of the table or in the References section.

## 10. Traceability Matrix

A cross-reference table linking requirements to threats, mitigations, and acceptance criteria:

| Requirement ID | Related Threats | Related Mitigations | Acceptance Criteria |
|---|---|---|---|
| FR-001 | — | — | AC-001 |
| SEC-003 | THR-001, THR-002 | MIT-001 | AC-005 |

---

## 11. Handling Long Tables

- If a requirement table exceeds one page, it continues on the next page with repeated column headers.
- If a single requirement's statement or acceptance criteria is very long, it wraps within the cell (no truncation).
- If the threat-model table exceeds one page, same repeat-header approach.
- Maximum cell text length: no hard limit, but a soft warning is logged if any cell exceeds 500 characters.

---

## 12. Error Handling

| Error | Handling |
|---|---|
| Template rendering error | Return HTTP 500 with error category `pdf_generation_error`. Log details. User can retry. |
| SRS JSON missing a required section | The section heading is included with a note: "This section was not generated." |
| File-system write error | Return HTTP 500 with error category. Suggest checking disk space. |
| PDF library unavailable | Return HTTP 500. Log dependency error. |
| Text encoding issues | All text is UTF-8 normalised before rendering. Invalid characters are replaced with `?`. |
| Very large SRS (> 100 requirements) | Log a warning for performance; no hard limit. |

---

## 13. Output Filenames

Generated PDFs are named:

```
{project_name_slug}_srs_v{version}_{date}.pdf
```

Where:
- `project_name_slug` = project name lowercased, spaces replaced with hyphens, special characters removed, truncated to 50 characters.
- `version` = SRS version number.
- `date` = generation date in `YYYYMMDD` format.

Example: `campus-firewall-project_srs_v1_20260807.pdf`

---

## 14. Reproducibility Metadata

To enable PDF reproducibility:

1. The PDF includes the generation metadata section (§9).
2. The `ExportedDocument` database record stores the SRS version ID, so the same JSON can be re-rendered.
3. Re-rendering the same SRS JSON with the same template should produce a visually identical PDF.
4. The PDF file hash is NOT guaranteed to be identical across renders (due to timestamps and PDF-library internals), but the content will be identical.
